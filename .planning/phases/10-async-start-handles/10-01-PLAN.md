# Phase 10, Plan 1: Async Start & Workflow Handles

## Objective

Stop forcing the caller to block for the lifetime of a workflow. A web request handler can start
a workflow and return immediately; a later request, in a different process, can fetch the result,
inspect the execution, or list what is running — all from a workflow ID.

## Context

### Today

`WorkflowStub.invoke` routes `@WorkflowMethod` to `startAndWait`, which subscribes to
`workflow-history:{workflowId}` and blocks on `resultFuture.join()` until a terminal event
arrives. There is no other path: nothing can start without blocking, and nothing can reattach to
a running execution to collect its result. `newWorkflowStub(iface, workflowId, taskQueue)`
returns a `SignalOnlyStub`, which rejects `@WorkflowMethod` outright.

### The API shape for starting without blocking

Java cannot express "call this typed method but do not run it" directly. Two established shapes:

1. Temporal's `WorkflowClient.start(stub::method, arg1, arg2)` — needs a family of functional
   interfaces (`Func0..FuncN`, `Proc0..ProcN`) to stay typed across arities.
2. A lambda that *does* call the method, with the stub in async mode:
   `client.start(() -> stub.process(order))`.

**This plan takes (2).** The stub's invocation handler checks a thread-local set by `start(...)`:
in async mode it appends `WorkflowStarted`, records the handle, and returns immediately instead
of waiting for a terminal event. Two functional interfaces (`Supplier` for a value-returning
workflow method, `Runnable` for `void`) cover every arity, because the arguments are supplied at
the call site by ordinary Java.

The roadmap wrote this as `WorkflowClient.start(stub, args)`; the lambda form is the same idea
with the arguments type-checked by the compiler instead of passed as `Object...`. It is the one
decision here worth overruling if the Temporal-compatible spelling matters more.

**Primitive return types matter.** In async mode the proxy must return a *type-appropriate*
default — `0` for `int`, `false` for `boolean`, `null` for references. Returning `null` for a
workflow method declared `int` would unbox to a `NullPointerException` inside the user's lambda,
at a point that looks nothing like the cause.

### Reading a result without a lost-notification window

`getResult()` must work whether the workflow is running or long finished. Ordering matters:

1. `tip = view.getLatestSeqnum()`
2. subscribe from `tip + 1` — anything terminal from here on completes the future
3. read history up to `tip` — if a terminal event is already there, complete immediately
4. await

Reading first and subscribing second would drop a terminal event landing in between. Subscribing
from `BEGINNING` instead would work but re-deserializes the whole history on every call — the
same cost Phase 9's review flagged on the query tag.

### `listWorkflows`

`WorkflowDispatcher` already maintains a Kryo-serialized `HashSet<String>` of in-flight workflow
IDs under the KV key `"active-workflows"` on `workflow-tasks:{taskQueue}`. Its constant is
private; make it public and read it rather than defining a second copy of the string.

Its meaning must be documented honestly: it holds what a worker on that queue has started and
not yet seen complete. It is not a query index — a workflow whose worker died without processing
its own terminal event lingers until a worker recovers it.

### Task 2 — `WorkflowHandle`

**File**: `WorkflowHandle.java`

```java
public final class WorkflowHandle<T> {
    public String workflowId();
    public T getResult();                        // blocks indefinitely
    public T getResult(Duration timeout);        // WorkflowTimeoutException on expiry
    public CompletableFuture<T> getResultAsync();
    public WorkflowExecutionDescription describe();
}
```

- `getResult` throws `WorkflowFailureException` for a failed workflow, exactly as
  `startAndWait` does today, so the failure contract does not change with the calling style.
- `getResultAsync` returns a future completed by the subscription; it must not leak the
  subscription — close it in a `whenComplete`.
- Deserializing the result needs no declared type: the payload is `writeClassAndObject`. The
  handle's `T` is therefore unchecked, as it is for the blocking stub today.

**Verification**: `mvn compile`.

### Task 3 — Async start mode in `WorkflowStub`

### Task 4 — `WorkflowClient.start`, `getHandle`, `listWorkflows`

**File**: `WorkflowClient.java`

```java
public <T> WorkflowHandle<T> start(Supplier<T> invocation);
public WorkflowHandle<Void> start(Runnable invocation);
public WorkflowHandle<Object> getHandle(String workflowId);
public <T> WorkflowHandle<T> getHandle(String workflowId, Class<T> resultType);
public List<String> listWorkflows(String taskQueue);
```

- `start` sets the thread-local, runs the lambda, reads the recorded workflow ID, and clears the
  thread-local in a `finally`. If the lambda completes without recording anything, throw
  `IllegalStateException` naming the likely cause (the lambda did not call a `@WorkflowMethod` on
  a stub from this client).
- Make `WorkflowDispatcher.KV_ACTIVE_WORKFLOWS` public and read it for `listWorkflows`.

**Verification**: `mvn compile`.

### Task 5 — Tests

**File**: `WorkflowHandleTest.java`

1. `start` returns without waiting — a workflow that parks on `Workflow.await` yields a handle
   promptly while the workflow is still running
2. `getResult` on that handle returns the value once a signal releases it
3. `getResult` on an **already-completed** workflow returns immediately (start blocking, let it
   finish, then `getHandle(...).getResult()`)
4. Cross-process reattach — a second `WorkflowClient` on the same log resolves the result by
   workflow ID alone
5. `getResult(Duration)` throws on a workflow that never finishes
6. `getResultAsync` completes and does not leave the subscription open
7. `getResult` on a failed workflow throws `WorkflowFailureException` with the original
   `errorType`
8. `describe()` reports `RUNNING` then `COMPLETED`, with type, task queue, and a `closedAt` that
   is null only while running
9. `describe()` on a failed workflow reports `FAILED` and the failure detail
10. `listWorkflows` contains a running workflow and not a completed one
11. `start` with a lambda that calls no workflow method throws `IllegalStateException`
12. A workflow method returning a primitive starts cleanly in async mode (the unboxing trap)
13. Starting the same workflow ID twice is idempotent — one execution, both handles resolve

**Verification**: `mvn verify` — 40 existing tests plus these still pass.

## Success Criteria

- [ ] A workflow can be started without blocking and its result collected later, in another
      process, from the workflow ID alone
- [ ] `getResult` returns immediately for an already-completed workflow, with no window where a
      terminal event can be missed
- [ ] `describe()` distinguishes RUNNING / COMPLETED / FAILED and carries the failure detail
- [ ] Blocking start behaviour and the existing failure contract are unchanged
- [ ] A primitive-returning workflow method starts in async mode without unboxing
- [ ] `mvn verify` green
