# Phase 8.1, Plan 1: Gumbo 0.6.0 Upgrade — Summary

## Status: Merged — PR #3, merge commit `7c4f804` (2026-09-02)

Inserted phase. Unplanned work: `mvn verify` hung indefinitely on `main`, which blocked
verifying Phase 9 and any future phase in one suite run.

## The Defect

`ChildWorkflowTest.childWorkflowFailurePropagatesToParent` blocked forever in
`WorkflowStub.startAndWait` at `resultFuture.join()`. The parent workflow's terminal event was
never delivered to the client. Reproduced on a clean worktree at `c492448`, so it predated the
Phase 9 query work.

Root cause was in **gumbo 0.2.0**, not Boudin. `SharedLogService.subscribe`:

```java
subscriptions.computeIfAbsent(tag, ...).add(sub);          // registered, backlogDone == false
Thread.ofVirtual().start(() -> {
    List<LogEntry> backlog = adapter.readByTag(tag, from.seqnum());  // (A) snapshot
    for (LogEntry e : backlog) sub.deliver(e);                       //     listener runs here
    sub.markBacklogDone();                                           // (B) live-eligible
});
```

and its append path:

```java
if (sub.isActive() && sub.isBacklogDone()) { /* deliver */ }
```

An entry appended between (A) and (B) was delivered by neither path — the snapshot predated it,
the notifier refused it — and there was no catch-up read after `markBacklogDone()`. It was lost
to that subscriber permanently.

**Why it presented as a Boudin flake.** The window is normally microseconds, so it only bit
under load: `ChildWorkflowTest` passed alone but hung once four other classes had run in the
same forked JVM. It struck that specific test because the failing-child path is the tightest
subscribe-then-append handoff in the codebase — the child watcher subscribes to child history
while the child throws on its first line, and the watcher's listener performs a blocking log
append *inside* the listener, widening the window further.

## Investigation Path

1. Confirmed pre-existing: full suite in a clean `git worktree` at `c492448` hung at the same
   test with the same stack, with none of the Phase 9 changes applied.
2. Ruled out a single-predecessor trigger: `ChildWorkflowTest` paired with each of
   `CrashRecoveryTest`, `GreetingWorkflowTest`, `TimerWorkflowTest`, `ActivityEnforcementTest`
   passed. The effect was cumulative, pointing at timing rather than shared fixture state.
3. Thread dump at hang time showed no live workflow virtual threads and an idle event loop —
   nothing was pending, so the event had never been delivered rather than being stuck in flight.
4. Read the gumbo 0.2.0 sources (from the sources jar in `~/.m2`) and found the window.
5. Wrote a deterministic reproduction, then found gumbo had already fixed it upstream.

## Resolution

Bumped `pom.xml` from gumbo `0.2.0` to `0.6.0`. gumbo 0.3.0 replaced the delivery mechanism:
one ordered delivery thread per subscription, and an append path that only enqueues instead of
deciding subscriber readiness — its changelog names both as the bug.

No Boudin code changes were needed. The upgrade compiles clean with no deprecation warnings;
Boudin never used `LogEntry.localId()` or `getLocalIdCountForTag`, so 0.3.0's
`localId` → `streamVersion` rename does not touch it, and Boudin's multi-tag appends do not use
the conditional `append(request, expectedVersion)` form whose signature changed.

## Test Results

- `SubscriptionCatchUpTest` — new regression guard. Fails on 0.2.0 (10s, zero deliveries),
  passes on 0.6.0 (0.86s).
- `mvn verify` — **37/37 tests pass, three consecutive green runs.** First time the full suite
  completes in a single JVM.

## Second Bug Fixed By The Same Upgrade

gumbo 0.6.0 also fixes multi-tag stream numbering, and its changelog describes Boudin's exact
pattern:

> "A worker cursoring a shared work queue holds a position and asks for what came after it.
> Under the old numbering an item enqueued by a workflow whose history sat at version 4 was
> numbered 4, so a worker that had already advanced to 8 behind a busier workflow was handed
> nothing... This is exactly the shape a workflow engine uses when one atomic append records
> history and enqueues the work item."

That is precisely Boudin's dual-tag atomic append to `workflow-history:{workflowId}` +
`activity-tasks:{taskQueue}`. On 0.2.0, an activity task could be silently skipped by a worker
reading the queue by version, with nothing in the log looking wrong. Boudin currently reads task
queues by seqnum rather than stream version, which is why this never surfaced as a visible
failure — but it was a live hazard for any version-keyed tail read, and Phase 12's task claiming
would have walked straight into it.

## Also Unlocked For Later Phases

- **0.4.0** added conditional mutation on the tag KV store (`compareAndSetTagValue`) — the
  primitive Phase 12's worker leases and task claiming need. It was listed as a Phase 12
  requirement and is now available.
- **0.5.0** added declared per-adapter capabilities (`LogCapabilities`:
  `conditionalAppend`, `compareAndSet`, `multiWriter`, `atomicMultiTagAppend`, …). Phase 12
  should refuse to start distributed execution unless the configured adapter declares
  `conditionalAppend` + `multiWriter`, rather than assuming it — note that
  `BatchingPersistenceAdapter` forces `multiWriter` off however capable its delegate is.

## Follow-Ups Not Taken

- Boudin's `ChildWorkflowStub.startChildWatcher` performs a blocking `sharedLog.append().join()`
  *inside* a subscription listener. gumbo 0.3.0+ serialises each subscription's deliveries on
  one thread, so this now delays only that subscription — but it is still the pattern that made
  the old window wide, and it stalls subsequent child-history deliveries. Worth moving the append
  off the listener thread.
- Boudin reads task queues by seqnum, so it does not yet benefit from 0.6.0's per-tag stream
  versions. Phase 12 should decide deliberately which of the two it cursors on.
