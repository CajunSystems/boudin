# Phase 9, Plan 1: Query Methods

## Objective

Make `@QueryMethod` work end-to-end. A client — in this process or another — can read the
current state of a running workflow synchronously, without waiting for it to complete and
without perturbing its history.

## Context

### Why queries are not `HistoryEvent`s

`workflow-history:{workflowId}` is replayed on every crash recovery, and `ReplayState`
pre-scans it. Query traffic is read-only control plane: it must not appear in replay, must not
grow the history, and must not affect determinism. Queries therefore get:

- their own sealed hierarchy `QueryMessage` in a new `query` package
- their own `LogSerializer` (`QuerySerializer`), same Kryo mechanics as `HistorySerializer`
- their own log tag `workflow-queries:{workflowId}`

`HistoryEvent`'s `permits` clause is **not** touched by this plan.

### Request/response protocol

```
Client                                    Worker (WorkflowRunner)
  subscribe workflow-queries:{wfId}
  from BEGINNING
  append QueryRequested(queryId, name, args) ──►
                                            query subscription fires
                                            resolve handler via WorkflowRegistry
                                            invoke on impl under signalLock
                                    ◄──────  append QueryCompleted(queryId, result)
                                             or QueryFailed(queryId, errorType, message)
  future completes; filter by queryId
  close subscription
```

`queryId` is a fresh UUID per request, so concurrent queries to the same workflow do not
collide. The client subscribes from `BEGINNING` and filters on its own `queryId` — same
pattern `WorkflowStub.startAndWait` already uses for `WorkflowCompleted`.

### Consistency model

The query handler is invoked while holding `WorkflowContext.signalLock`, the same lock
`deliverSignal` holds. A query therefore never interleaves with a signal handler. It *can*
observe the workflow thread mid-method between yield points — this is the same model Temporal
uses, and the `@QueryMethod` javadoc already states handlers must not modify state.

### No running worker

If no `WorkflowRunner` on any worker holds the workflow, nothing answers and the client times
out. Rather than surfacing a bare timeout, the client throws `WorkflowQueryException` with
errorType `QueryTimedOut`, whose message names the likely causes (workflow completed, or no
worker polling that task queue). Answering queries against completed workflows by replaying
history is deferred — Phase 10 adds `describe()` for terminal state.

### Existing patterns to follow

- Kryo arg encoding: `KryoSerializer.toBytes(args != null ? args : new Object[0])`, decoded as
  `(Object[]) KryoSerializer.fromBytes(payload)` — exactly as `deliverSignal` does.
- Null/void result: `WorkflowStub.startAndWait` treats `null`/empty bytes as `null`.
- Subscription cleanup in a `finally` with a swallowed close exception.

## Tasks

### Task 1 — Create the `query` package

**File 1**: `src/main/java/com/cajunsystems/boudin/query/QueryMessage.java`

Sealed interface with `queryId()` accessor and three records:

```java
public sealed interface QueryMessage
        permits QueryMessage.QueryRequested,
                QueryMessage.QueryCompleted,
                QueryMessage.QueryFailed {

    String queryId();
    Instant timestamp();

    record QueryRequested(
            String queryId,
            Instant timestamp,
            String workflowId,
            String queryName,
            byte[] args           // KryoSerializer.toBytes(Object[])
    ) implements QueryMessage {}

    record QueryCompleted(
            String queryId,
            Instant timestamp,
            String workflowId,
            byte[] result         // KryoSerializer.toBytes(returnValue)
    ) implements QueryMessage {}

    record QueryFailed(
            String queryId,
            Instant timestamp,
            String workflowId,
            String errorType,
            String message
    ) implements QueryMessage {}
}
```

**File 2**: `src/main/java/com/cajunsystems/boudin/query/QuerySerializer.java` — mirrors
`HistorySerializer`: `implements LogSerializer<QueryMessage>`, `INSTANCE` constant, delegates
to `KryoSerializer`.

### Task 4 — Worker-side query handling

**File 1**: `src/main/java/com/cajunsystems/boudin/workflow/WorkflowContext.java`

Add:

```java
/**
 * Invokes a query handler on the workflow implementation while holding {@link #signalLock},
 * so a query never interleaves with signal delivery.
 */
public Object invokeQuery(Method queryMethod, Object impl, byte[] argBytes) throws Exception
```

Decodes args like `deliverSignal`, invokes under `synchronized (signalLock)`, unwraps
`InvocationTargetException` to the user's cause, and does **not** call `notifyAll()` — a query
changes nothing, so there is nothing to wake.

**File 2**: `src/main/java/com/cajunsystems/boudin/internal/WorkflowRunner.java`

- New field `querySubscription`
- In `start()`, after the history subscription: subscribe to `workflow-queries:{workflowId}`
  from `LogPosition.BEGINNING`, deserialize with `QuerySerializer`, and for
  `QueryRequested` only, submit `onQueryRequested(...)` to the event loop
- `onQueryRequested`: dedupe on `queryId` (a `Set` field, same pattern as
  `processedEventSeqnums`); resolve via `workflowRegistry.findQueryMethod(workflowType, name)`;
  unknown name → append `QueryFailed` with errorType `UnknownQuery`; handler throws → append
  `QueryFailed` with the cause's simple name; success → `QueryCompleted` with
  `KryoSerializer.toBytes(result)` (or empty bytes for null)
- Run the handler + append on a virtual thread, not on the event loop thread — the append
  blocks on `.join()` and must not stall dispatch for every other workflow on this worker
- `close()` also closes `querySubscription`

**Verification**: `mvn test` — all pre-existing tests pass.

### Task 5 — Client-side query round trip

**File 1**: `src/main/java/com/cajunsystems/boudin/api/QueryClient.java` (package-private)

One static method shared by both stubs:

```java
static Object query(SharedLog sharedLog, String workflowId, Method method,
                    Object[] args, Duration timeout) throws Exception
```

- resolves the query name from `@QueryMethod.name()` or the method name
- subscribes to `workflow-queries:{workflowId}` from `BEGINNING` **before** appending
- appends `QueryRequested`
- waits `timeout` on a `CompletableFuture`; on timeout throws `WorkflowQueryException` with
  errorType `QueryTimedOut` and a message naming the likely causes
- on `QueryFailed`, throws `WorkflowQueryException` carrying the worker-side errorType
- closes the subscription in a `finally`

**File 2**: `WorkflowStub` — replace the `UnsupportedOperationException` branch with a
`QueryClient.query(...)` call; throw `IllegalStateException` if `workflowId` is still null
(same guard `sendSignal` uses). Update the class javadoc.

**File 3**: `SignalOnlyStub` — same, using the constructor-supplied `workflowId` and the
default query timeout. Update the class javadoc to say signal-and-query.

**Verification**: `mvn compile` passes.

### Task 6 — Tests

**File**: `src/test/java/com/cajunsystems/boudin/QueryWorkflowTest.java`

Follow `GreetingWorkflowTest` structure — in-memory Gumbo adapter, Awaitility for async waits,
AssertJ assertions, fresh log and worker per test.

Workflow under test: parks on `Workflow.await(() -> approved)`, exposes
`@QueryMethod String getStatus()` and `@QueryMethod int getItemCount()`, plus an `approve`
signal.

Cases:
1. Query a running workflow mid-execution returns live state
2. Query reflects a state change made by a signal (query after signal sees the new value)
3. Query via a signal-only stub (the cross-process path)
4. Query with no arguments and a query with an argument both round-trip
5. Unknown query name → `WorkflowQueryException` with errorType `UnknownQuery`
6. Handler that throws → `WorkflowQueryException` carrying the cause type
7. Query against a workflow no worker is running → `WorkflowQueryException` /`QueryTimedOut`
   (use a short `queryTimeout` so the test stays fast)
8. Registration of a workflow whose `@QueryMethod` returns `void` → `IllegalArgumentException`

**Verification**: `mvn verify` — all tests pass.
